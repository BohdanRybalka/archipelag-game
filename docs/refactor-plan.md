# План рефакторингу «Архіпелагу»

Специфікація для поступового переписування коду гри в зрозумілу структуру **без зміни поведінки**. Кожен крок має Entry criteria (що має бути правдою до старту) і Exit criteria (як перевірити, що крок завершено).

## Як користуватись документом

- Для сесії, яка реалізує крок: прочитай розділи 1–5, потім лише свій крок. Виконуй кроки по черзі: наступний починається, коли попередній злитий у `main`.
- Один крок = один PR. В описі PR: що зроблено, виводи перевірок, відхилення від специфікації і чому.
- Після злиття онови таблицю статусу (розділ 5) в тому ж PR.
- Якщо специфікація суперечить коду (рядки зсунулись, функцію перейменовано), орієнтуйся на назви функцій і мету кроку, а не на номери рядків. Відхилення опиши в PR.

Що вже добре і має лишитись:
- правила (`logic.js`) не знають про DOM і three.js, тому бот ганяє ту саму логіку в Node;
- функції правил змінюють стан і повертають події (`applyTide` → `{flooded, lost, grow…}`), а рендер їх відтворює;
- генерація карт детермінована (`seed`);
- анімації — Promise-твіни, послідовності читаються як сценарій (`runTide`).

Що заважає (цифри для порівняння після рефакторингу):
- у `game.js` 120 функцій і ~26 змінних стану (`st`, `BD`, `mode`, `tool`, `hover`, `line`, `undo`, `ghost`…) в одному замиканні;
- режим гри дублюється в DOM: 16 звертань до `document.body.classList`, з них 4 читають клас `in-game` як стан (`save()`, `measureRect()`, `openHelp()`, hot-reload); 25 перевірок `mode ===`;
- 26 розгалужень `tool === '…'` у прев'ю, вводі, будівництві;
- 9 копій правила `r.ok || r.why === 'wood' || r.why === 'stone'`;
- мертвий код версії 2 (мости, причали, пором): ~170 рядків цілих функцій + гілки всередині інших; `case BT.PIER` порівнює з `undefined`;
- `ver++` (ручне скидання кешу) у 7 місцях;
- текст розходиться з правилами: `SAW_MAX = 2`, а підказка лісопилки каже «до 3»;
- 55 рядків `game.js` довші за 160 символів; однобуквені імена модульного рівня (`L`, `BD`, `D`, `M`, `E`, `B`, `F`);
- HTML збирається рядками через `innerHTML`.

Безпека (PR #1): `loadSave()` перевіряє збереження з `localStorage`, three.js підключено з `integrity` (SRI). Обидва механізми мають пережити всі кроки.

## 2. Принципи (обов'язкові для всіх кроків)

1. **Поведінка не змінюється.** Ні правила, ні баланс, ні вигляд, ні тексти (крім явно названих у кроці виправлень).
2. **Деплой не змінюється.** Результат — один `index.html` у корені, закомічений; three.js з cdnjs з тим самим SRI; шрифти як зараз.
3. **Без нових runtime-залежностей.** Залежності лише для розробки (`devDependencies`).
4. **Сумісність збережень.** Збереження формату `v: 4`, зроблене поточною версією, має завантажуватись після кожного кроку. Формат стану не змінювати; якщо крок 1 прибирає поле `bridges`, старі збереження з `bridges: []` все одно мають завантажуватись.
5. **`archive/` не чіпаємо.**
6. **Механічні зміни окремими комітами.** Форматування, перенесення файлів, перейменування — кожне окремим комітом, щоб змістовні зміни було видно в diff.

## 4. Середовище (хмарна сесія Claude Code)

- **cdnjs недоступний через проксі** контейнера. Для перевірок у браузері three.js підставляється з `node_modules/three/build/three.min.js` (пакет `three@0.128.0` ставиться з npm, реєстр доступний). Його sha512 збігається з SRI в `tools/build.js`.
- **Через SRI підставлена відповідь мусить мати заголовок `Access-Control-Allow-Origin: *`.** Інакше браузер заблокує скрипт і гра не запуститься (виглядає як порожня сторінка без помилок у грі).
- **Playwright:** у контейнері браузери лежать у `/opt/pw-browsers`, `playwright install` не запускати. Якщо версія з `package.json` не збігається з встановленими браузерами, запускати з `executablePath` (скрипт перевірок має приймати змінну `CHROMIUM_PATH`).
- **Повний бот працює ~2 хв** (довше за стандартний тайм-аут команди 120 с). Запускати у фоні або з більшим тайм-аутом. Швидкий «зліпок» (крок 0) — ~6 с.
- **Хук для автоматизації:** `window.__arch` у `game.js` (`start`, `build`, `dams`, `next`, `undo`, `state`, `screen`). Його лишаємо: на ньому тримаються перевірки в браузері.

   ```
     app/         main.js (старт, потік рівня), session.js, save.js (store, loadSave, save)
     view3d/      scene.js, materials.js, geometry.js, models.js, board.js, roads.js,
                  decals.js, effects.js, camera.js, seasons.js
     ui/          text.js (plural, esc, svgI/ICON), hud.js, chips.js, menu.js, hints.js, help.js
     input.js, audio.js, tween.js
   ```
5. **Збірка:** `tools/build.js` викликає esbuild API: вхід `src/app/main.js`, `format: 'iife'`, без мінімізації, `THREE` лишається глобальним (з CDN). Бандл вставляється в шаблон як зараз, результат — один `index.html`.
6. **Node-інструменти** (`balance-bot`, `calibrate`, `maps`, `check-map`, `check-*`) переходять на ESM (`"type": "module"`) і імпортують `src/core`.
7. **Опційно:** ESLint з `no-unused-vars` і `import/no-cycle`.

### Чого не робимо
- Не змінюємо логіку режимів, не перейменовуємо (крім механічного `st` → `session.st` там, де це потрібно для модулів), не переписуємо HTML.

### Exit criteria

- [ ] `src/core` нічого не імпортує з `app`, `view3d`, `ui`: `grep -rE "from '\.\./(app|view3d|ui)" src/core` → порожньо.

- [ ] Жоден модуль не довший за ~400 рядків (винятки перелічити в PR з причиною).
- [ ] `index.html` відкривається подвійним кліком з диска (`file://`) — перевірити вручну.
- [ ] `check:logic` без змін (після переходу на ESM); вивід бота = `bot-full.txt`.
- [ ] `check:ui` зелений; скриншоти U5 візуально як до кроку.
- [ ] README: нова структура, команди (`npm install`, `npm run build`, `npm run check`).
- [ ] Загальний DoD.

### Ризики й підказки
- ES-модулі не можуть перепризначати `let`, імпортовані з іншого модуля. Тому спільний стан мусить бути полями об'єкта (`session`), а не окремими змінними.
- Порядок ініціалізації: зараз код виконується згори вниз в одному замиканні (сцена створюється до моделей). У модулях ініціалізацію зібрати в явні функції `init…()`, які викликає `main.js` у тому самому порядку.

## Відкриті рішення (з типовими варіантами)

Якщо власник не вирішив інакше, сесія діє за типовим варіантом і згадує це в PR.

1. **esbuild як devDependency (крок 3).** Типово: так. Альтернатива — склеювати IIFE-файли по черзі в `build.js` без залежностей, але тоді модулі спілкуються через глобальний об'єкт і явних залежностей не видно.
2. **Крок 5.** Типово: пропустити, якщо нових інструментів не планується. На 4 інструментах користь помірна.
3. **`st` → `state` (крок 6).** Типово: так, окремим механічним комітом.
4. **Джерело кольорів (крок 6).** Типово: CSS-змінні.
5. **Мінімізація бандла.** Типово: ні, щоб вихідний код сторінки лишався читабельним (розмір і так ~170 КБ).

## Що свідомо не робимо

ECS, Redux, фреймворк для UI (React, Preact), повний перехід на TypeScript, класи для всього, DI-контейнер. Для гри на ~3,4 тис. рядків це додасть коду й концепцій, а не прибере. Опційна альтернатива TypeScript — JSDoc-типи з `// @ts-check`.
